## Operational table improvements

Receiving supports PO/vendor/part lookup, readable PO/vendor/part identity, stable selected PO links, and an explicit 30/90/180/365-day history scope. Receipt and inspection errors stay inside their owning dialog. Shipping supports shipment/work-order/part/customer/tracking lookup, status/date scopes, all-page loading and local page navigation. Date copy specifies dispatch date or creation date for pending shipments. Purchasing's status view loads the requested server population without changing global Open PO counts.

Warehouse and Receiving derive their active tabs directly from the committed query string. This fixes the race where an immediate local tab update survived a cancelled router transition and disagreed with Back even though the URL had restored correctly. Clicking an already selected tab leaves history unchanged. Permanent coverage is in [Warehouse.receivingTabs.test.tsx](../../frontend/src/pages/Warehouse.receivingTabs.test.tsx).

New detail forms use labelled controls, pending/error states and the shared unsaved-change guard. Supplier and certification selectors no longer require operators to know database IDs. Historical documents retain their linked part number even when the part is inactive; lookup loading is independent from document filtering.

## Correctness review resolutions

An independent reviewer reproduced three edge defects during implementation. All are corrected with permanent tests in [backend/tests/api/test_ux_operations.py](../../backend/tests/api/test_ux_operations.py):

- A draft line-note change now updates the parent PO timestamp. The first save succeeds, a second save using the original token returns 409, and the first note remains intact.
- Explicit `quantity_rejected: null` returns 422; omitting that field still permits unrelated NCR updates.
- Shipped-to-delivered succeeds and sets actual delivery date when absent. It does not repeat dispatch or close an unrelated partial remainder; reopening, cancelling dispatched shipments and editing their quantities remain rejected.

The review also identified ambiguous document revision identity. Upload now locks the selected predecessor, rejects an existing newer child (409), and rejects an ancestor label reused with different casing (422). Tests preserve A and B, reject A→B→A and reject a second child from superseded A. See [independent review](operations-correctness-review.md) for scope and limits.

## Migration and deployment boundary

Migration `090_document_revision_chain` follows `089_quote_line_conversion`. It adds a nullable document predecessor FK and a company/predecessor index; historical rows remain valid independent roots. The migration tests exercise SQLite upgrade/downgrade/upgrade and compile PostgreSQL upgrade/downgrade SQL. They do not substitute for a staging PostgreSQL upgrade or concurrent lock-contention test.

No existing files are relabelled or deleted. Linked revision files cannot be removed through the document delete endpoint. Document history currently reads the tenant's document rows before traversing the lineage; no measured performance gain is claimed for this operation. List endpoints with all-page clients favor complete visible populations; high-volume pagination performance should be measured against representative staging data.

The shipping API retains existing dispatch audit, inventory, certificate and event behavior on actual dispatch. Record-as-sent remains a manual purchasing workflow action; the app makes no unsupported claim of supplier email delivery. Local browser acceptance uses synthetic SQLite records and PDF files. Carrier-provider writes and production deployment remain outside this implementation verification.

The browser evidence covers specific exercised paths and viewports. It does not establish every-device, every-role or full assistive-technology conformance.
