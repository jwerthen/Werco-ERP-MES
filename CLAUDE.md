# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Werco ERP-MES is a custom Enterprise Resource Planning + Manufacturing Execution System for precision manufacturing, built for **AS9100D and ISO 9001** compliance on a secure-by-default multi-tenant foundation. The posture is not incidental — tenant isolation, audit trails, traceability, and access control are correctness requirements, not features. See the "Compliance-critical invariants" section below before changing data-writing code.

**CMMC Level 2 is not being pursued at this time** (deprioritized 2026-07-28). `docs/CMMC_LEVEL_2_COMPLIANCE.md` is frozen as a historical record: don't add change-log rows to it, and don't add new CMMC-only controls. This descoped the certification *paperwork*, not the protections — every security control already in the code stays, because it protects tenant data on its own merits. If a future customer contract carries a DFARS 252.204-7012 flow-down, revisit this decision before assuming the obligations are optional.

## Subagent delegation policy

This repo ships a team of specialized subagents in `.claude/agents/`. Route work to them automatically — don't wait to be asked by name:

- **backend-engineer** — FastAPI endpoints, services, models, schemas.
- **frontend-engineer** — React/TS pages, components, forms, styling.
- **database-migration-specialist** — any Alembic migration (schema/enum/constraint change).
- **ai-integration-specialist** — Anthropic-powered RFQ parsing / quoting / learning.
- **devops-engineer** — Docker, CI/CD, Railway/Vercel, workers, env/secrets.
- **github-manager** — PRs, issues, releases/tags, labels, branch protection, CODEOWNERS; drives merge-when-green via `gh` (waits on the review gates; doesn't edit the Actions YAML — that's devops-engineer).
- **compliance-auditor** — review for tenant isolation, audit logging, RBAC, soft-delete, traceability.
- **code-reviewer** — diff review for correctness + cleanups, runs the lint/type/security gate.
- **test-engineer** — pytest / Jest / Playwright coverage.
- **documentation-engineer** — README, docs/ runbooks, CLAUDE.md, API/OpenAPI, compliance docs.

**Definition of done for any code change.** A change is not complete until:
1. The **test-engineer** has added or updated tests for the changed behavior (and they pass), AND
2. The **documentation-engineer** has updated the docs the change actually affects — **API endpoints, roles/permissions, env vars, and deploy steps are the four that must never go stale** (`docs/API.md`, `docs/RBAC_PERMISSIONS.md`, `docs/ENVIRONMENT_VARIABLES.md`, `docs/DEPLOYMENT*.md`) — plus any runbook whose documented behavior changed (or has confirmed none are affected). Narrative/roadmap docs are updated when they'd otherwise become false, not as a matter of routine, and the frozen `docs/CMMC_LEVEL_2_COMPLIANCE.md` is explicitly **out of scope** — no new change-log rows.

Invoke these two after the implementing agent finishes, as a matter of course — they are the standing QA and documentation gates, not optional extras. For changes touching **authentication, tenancy scoping, deletion, or audit-writing paths**, also route through **compliance-auditor** before considering the work done. Skipping these is only acceptable for genuinely non-code changes (e.g. a typo fix in a comment) — and say so explicitly when you skip.

## Backend architecture

Layered FastAPI app under `backend/app/`:

- `main.py` — app factory, middleware wiring (CORS, GZip, rate limiting via slowapi, Sentry, Host-header allowlist via TrustedHostMiddleware, and `limit_json_body_size`, the `MAX_JSON_BODY_BYTES` cap (256 KB, **413** over it, checked on `Content-Length` *and* on the bytes actually read; `MAX_SANITIZED_JSON_BODY_BYTES` still works as a deprecated alias) — it runs **before route auth**, so the cap is what stops an unauthenticated caller choosing how many bytes the app buffers and hands to `json.loads`; multipart uploads and carrier webhooks are deliberately exempt). **There is no ingest-time sanitization**: this middleware used to bleach-strip and rewrite every JSON body, which corrupted persisted quality records (ASME Y14.5 `<REF>`/`<TYP>` silently stripped) while protecting nothing. Removed 2026-07-30 with the `bleach` dependency. **Store request bytes verbatim; escape at the sink** — the only backend sink that interprets markup is reportlab `Paragraph`, escaped via `services/pdf_text.py::pdf_escape`. Don't reintroduce an HTML sanitizer for input handling; two guard tests (`test_frontend_no_raw_html_render_guard.py`, `test_pdf_text_escaping.py`) hold the argument up. See `docs/SECURITY_ADVISORY_SUPPRESSIONS.md` → bleach removed.
- `api/endpoints/` — ~60 REST routers, one per domain, mounted under `/api/v1/`. Thin: validate, call a service, return a Pydantic schema.
- `api/deps.py` — **the dependency-injection seam.** Auth, tenancy, and RBAC all flow through here. Use these rather than re-implementing:
  - `get_current_user` / `get_current_active_user`
  - `get_current_company_id` — returns the *active* company (handles platform-admin context switching; do not read `current_user.company_id` directly for scoping)
  - `require_role([UserRole.X, ...])`, `require_platform_admin`, `get_admin_user`
  - `get_audit_service` — request-scoped `AuditService`
- `services/` — business logic. Multi-step / state-changing operations belong here, not in routers.
  - **All Anthropic LLM calls go through `services/llm_client.py`** (`run_llm_task`: model routing via `llm_model_router`, prompt caching, per-call usage telemetry into the tenant-scoped `ai_usage_events` table — telemetry, not audit data). Don't instantiate `anthropic.Anthropic` at call sites.
  - **Prompt text is versioned in `services/prompts/`** — bump the prompt's semver `version` and add a `CHANGELOG.md` entry there whenever prompt text or request layout changes; the version is recorded on every usage row.
  - **Completion inventory effects** live in `completion_inventory_service.py` (FG receipt + BOM backflush) and `material_consumption_service.py` (tied-material consumption), both driven from the single `apply_completion_inventory_effects` seam — add **work-order**-completion side-effects there, not at the call sites. Its **operation**-level twin is `apply_operation_completion_inventory_effects` (same module), called right after `finalize_operation_completion` on all four operation-completion handlers; operation-scoped tied-material consumption fires there, while the FG receipt and the BOM backflush deliberately stay work-order-scoped. **The BOM backflush leg is gated on `Part.backflush_components`, which is now settable (PR 4.5) — but only through `PUT /parts/{id}` / `PUT /materials/{id}`, behind the shared refusal gate `parts.assert_backflush_change_allowed` (409 while `backflush_readiness_for_part` reports a blocking diagnostic). It stays opt-in and default-off — the field is deliberately absent from `PartBase`/`PartCreate`, so no create path and no CSV importer can set it — and *no production job has yet exercised the leg*, so treat its behavior as unproven and change it only with that in mind. At completion the leg **refuses rather than guesses**: every `blocking` diagnostic the resolver raises drops the demand it describes (that component when the diagnostic names one, the whole leg when it names none) and writes a `BACKFLUSH_DEMAND_REFUSED` chain row. That refusal is the **net**, not a second gate — the opt-in check runs once, at the flip, covers the **BOM half only** (routing conditions need a work order and are never evaluated at part scope), and every input it read stays editable afterwards by anyone with `boms:edit` / `routings:edit`, with nothing on those edit paths aware the part is armed.** See invariant 6.
  - **Operation READY promotion is either a sequenced ROUTING or a work-center DISPATCH POOL, and which one is the work order's own setting** — `WorkOrder.sequential_operations` (migration `081`). `True` = a routing: an operation reaches READY only once **every** lower-sequence operation is COMPLETE, its own work center included. `False` = a pool: operations sharing a work center don't block each other, promote together, and are mutually startable — the pre-`081` rule, byte-for-byte. **Cross-work-center ordering holds either way**, so the two modes are indistinguishable on a routing whose steps each sit at a different work center. The promotion rule and the clock-in gate are deliberately **one rule** — keep them that way. The promotion itself is **one implementation, `promote_ready_operations`, reached from FOUR seams**: `release_first_ready_operation` (WO release), `release_next_ready_operation` (after each operation completion), `_promote_stranded_ready_operations` (called **last** inside `reconcile_work_orders_from_completion_evidence`, i.e. the **read path**), and `shop_floor.resume_operation` (which lands the resumed op at PENDING and delegates any lift back to READY to the rule, so a resume can never perform a release). The seams differ only in how they obtain the operation list — don't re-inline the rule at a fifth one; copies of a gate is how the office and floor rules drifted apart in the first place. All four promote **every** PENDING operation whose predecessor gate passes, not just the lowest-sequence one.
    - **`work_order_allows_same_work_center(wo)` is THE single reader of the column** (returns `not sequential_operations`), and both predicates take the value from it: `promote_ready_operations` resolves it once per call and hands it to `operation_blocked_by_incomplete_predecessors` (the in-memory twin), while `operation_action_gates.operation_blocked_by_predecessors` hands the same resolved value to `has_incomplete_predecessors` (the SQL twin). Same resolver, same work order — that is what keeps promotion and every action gate one rule. It returns **pooled (`True`) whenever the flag can't be read** (`None` work order, a stub predating the column), the pre-`081` value every caller used to hard-code, so an unresolvable WO can never silently *tighten* a gate and strand work the floor was already allowed to start. **The two defaults differ on purpose**: `server_default="false"` backfills every pre-`081` row to pooled (exactly what it was released and scheduled under — nothing in flight changes rules underneath the floor), while `default=True` makes every new work order a sequenced routing. No backfill pass, no `UPDATE`; converting an existing job is an explicit audited flip. `PUT /work-orders/{id}` is that flip verb (ADMIN/MANAGER/SUPERVISOR, already `version`-gated): turning it **on** refuses **409** on a laser WO, and **409 naming the operations** when any operation the strict rule would block has already been worked (IN_PROGRESS / `actual_start` / booked qty / any `TimeEntry`) — both raised *before the first `setattr`*, because every completion verb re-evaluates the gate at action time, so such an operation would become **uncompletable** the instant the flag flipped and no read path would heal it. Otherwise it demotes un-worked blocked operations READY→PENDING via `demote_operations_for_sequencing`, one `log_status_change` row each — **the only place anything moves an operation backwards as a rule**, and it exists because promotion is forward-only. Turning it **off** needs no sweep (the read heal re-promotes the pool). `work_order_duplicate_service._copy_header` carries the flag (plan, not production record); `work_order_blocker_service._resume_operation_if_no_open_blockers` lands an un-started blocked operation at PENDING rather than READY, since READY would be a card every start verb refuses that the PENDING-only read heal would never fix.
    - **The read seam exists because release and completion are unreachable for an already-released WO.** `POST /work-orders/{id}/release` refuses anything not DRAFT, so a work order released *before* the pooling rule shipped had its operations promoted one-at-a-time and no way to re-run the new rule — they sat PENDING forever, invisible to the kiosk and dispatch board (both surface READY only). A read now repairs it: no new endpoint, no migration, no owner action. It **never promotes a DRAFT work order** — standing owner decision, Release is the authorization step and the record of who authorized production, so a GET must not put unreleased work on the floor's board — and skips TERMINAL WOs (status re-read *after* the WO-level sync, so a WO that just completed is not re-promoted). It is read-safe (each WO guarded individually so a failure can't 500 a board load), idempotent (only PENDING rows are read and written, so a second read emits no duplicate `operation_ready`), and deliberately **not** appended to `transitions` — that list is a *completion* contract whose five consumers write audit rows, emit `operation_completed`, and run inventory/cost/scheduling effects. Traceability for the flip stays the tenant-scoped `operation_ready` OperationalEvent, as at the other seams.
    - **Which reads heal, and which don't.** Only the handlers that call the reconcile: `GET /work-orders`, `GET /work-orders/{id}`, `GET /shop-floor/dashboard` (bounded by `SHOP_FLOOR_DASHBOARD_RECONCILE_LIMIT`), `GET /shop-floor/operations`, and `GET /shop-floor/operations/{id}`. The **kiosk queue and the dispatch-board endpoints do not reconcile**, so opening the work order or a shop-floor list is what repairs a stranded WO — polling the board forever will not. That is also what **converges an existing work order onto a changed `sequential_operations` setting** (turning it off in particular, which does no sweep of its own). (`POST /work-orders/` also reconciles — six handlers in all — but a new WO is DRAFT, so the carve-out makes it the no-op it has always been.)
    - Promotion is a *visibility* rule, not a grant: `has_incomplete_predecessors` has always let the floor clock into same-work-center operations on a pooled WO in any order, and the dispatch board and kiosk surface READY work **only** (`dispatch_service.QUEUE_OPERATION_STATUSES`), which is how a batch WO carrying ~18 press-brake items showed 1. `work_order_state_service.operation_blocked_by_incomplete_predecessors` is the in-memory replica of that query (it exists to keep `release_next_ready_operation` off the PERF-4 N+1) — "replicates EXACTLY" is a claim both rules depend on, so edit the branch and the SQL together, including the new `allow_same_work_center` parameter both now take. Three things are load-bearing: (a) the **ON_HOLD carve-out** — a held predecessor blocks from **any** work center, its own included, so a quality/material stop takes the whole pool off the board instead of leaving the siblings startable; because the predicate is shared this tightens clock-in too, which is the intent, not a side effect; (b) the **laser** dispatch-pool exemption (`is_laser_dispatch_work_order`) is **strictly fuller** and must not be collapsed into the same-work-center allowance *or* into the `sequential_operations` flag — it drops predecessor gating entirely, so nests promote across two lasers, and it short-circuits **above the flag at every seam**, so a **held nest does not block its siblings** and the column is inert on those rows (both laser WO constructors pin it `False` so a nest package can't serialize a claim its own behavior contradicts); (c) **no inline copies of the gate remain anywhere.** The office verbs `POST /work-orders/operations/{id}/start|complete` were moved onto `operation_action_gates.operation_blocked_by_predecessors` first; `081` moved the **shop-floor** twins `PUT /shop-floor/operations/{id}/start` and `POST /shop-floor/operations/{id}/complete`, which until then still carried their own copies hard-coding `allow_same_work_center=True` — left alone they would have kept **pooling on the operator's primary verbs while the board honored the WO's setting**, i.e. an operation hidden from the dispatch board but startable by badge scan. `migration_import_service.import_open_work_orders` deliberately keeps its own promote-exactly-one inline rule — and it now *agrees* with the read seam rather than being converged away from it, because it doesn't pin the flag, so an imported WO takes the sequenced create default and the strict rule promotes exactly the one operation the loader already did. Office `start` is role-gated (ADMIN/MANAGER/SUPERVISOR/QUALITY) to match its `complete` twin; the shop-floor `PUT /shop-floor/operations/{id}/start` stays operator-open.
    - **This is a visibility-and-action rule, NOT an airtight enforcement control — don't document or design against it as one.** Four write paths still reach COMPLETE or READY with **no predecessor check**: (a) `_sync_operation_status_from_quantity` flips an operation to COMPLETE from closed labor evidence on the **read path**, ungated; (b) `_copy_slot_completion_evidence` likewise, for regenerated sibling rows sharing a progress key; (c) `POST /work-orders/{id}/complete` force-completes every open operation, ungated (it does refuse **409** on an ON_HOLD one); (d) `PUT /work-orders/operations/{id}` refuses only `status` COMPLETE, so a supervisor can hand-set an operation to **READY** through its blind `setattr` loop — a deliberate, role-gated (ADMIN/MANAGER/SUPERVISOR), fully-audited supervisor override, and the read heal will never re-demote it because that heal reads PENDING rows only. Separately, `scheduling.py::_apply_work_order_schedule` promotes PENDING→READY with no gate but is **provably safe**: it only ever promotes `current_op`, which `_get_current_operation` defines as *operations sorted by sequence → the first not-COMPLETE one*, so every lower-sequence operation is COMPLETE by construction and the strict rule — which blocks only when some lower-sequence operation is **not** COMPLETE — can never block it. Stated so nobody "fixes" it into a fifth copy of the rule.
  - **Shop-floor operation completion requires a labor record, and the office twin deliberately does not.** `POST /shop-floor/operations/{id}/complete` refuses **400** (`MSG_NO_LABOR_RECORDED`) an operation with **zero** `TimeEntry` rows — `operation_action_gates.operation_has_labor_evidence`, tenant-scoped, existence only. It is **not** "the caller is clocked in right now": **any** entry counts, open or closed, because the kiosk clocks out *before* completing and the crew station's signing badge often holds no entry of its own — an open-entry rule would break both. `POST /work-orders/operations/{id}/complete` is exempt on purpose: desk cleanup of never-clocked work is a supervisor/quality decision the owner kept. **That asymmetry is an owner decision, not an oversight — don't "align" the two**; a test pins it, and `complete_blockers`' docstring says so. Distinct from the `no_labor_recorded` quality exception, which stays warn-and-record at WO completion.
  - **Duplicating a work order** goes through `services/work_order_duplicate_service.py` (`duplicate_work_order`, behind `POST /work-orders/{id}/duplicate`) — it copies the *plan* (operations + instructions, laser nests incl. the `document_id` **reference**, open material ties, and a **re-snapshot** of process-sheet steps from each family's currently-released revision) onto a new DRAFT WO and leaves the *production record* behind. The rule for any new column: instructions carry, the record does not — and `parent_work_order_id`, `must_ship_by`, `run_order` and the scheduled dates are deliberate omissions, not oversights (see the module docstring). It flushes but never commits; the caller wraps it in `atomic_transaction`. Two properties are load-bearing: a nest-bearing duplicate's `quantity_ordered` is **derived** from the copied nests' `planned_runs` (the request value is ignored), and every copied tie lands inert with its **lot pin cleared**. Skips are returned to the caller *and* written to the audit row — don't demote either channel to a log line.
  - **Named work-order templates** live in `services/work_order_template_service.py` (behind `/api/v1/work-order-templates`, ADMIN/MANAGER/SUPERVISOR on every verb). A template is a **name plus a POINTER** at the work order whose plan it stands for — never a stored plan — and "use" hands that work order to `duplicate_work_order`, so it can never mint a work order the duplicate path would not, and the result lands **DRAFT with PENDING operations**. Import Nest Package still force-sets RELEASED and is unchanged; templates are the draft door. **One use can create up to 20 SEPARATE drafts** (`count`, cap `MAX_TEMPLATE_USE_COUNT`, 422 above it), each its own work order at the SAME `quantity_ordered` — a weld assembly is one unit per work order, so "five of these" is five work orders, never one at five — with an optional `unit_numbers` list, one per draft in creation order, blanks stored NULL. The units are **supplied, never generated** (owner decision: real unit numbers are not a trailing-digit increment), applied by the TEMPLATE SERVICE after each copy returns rather than by `_copy_header`, whose deliberate non-carry of `unit_number` is pinned by one test class and must stay. Duplicate units are refused **within** a request only — `work_orders.unit_number` has no unique constraint because rework re-uses a unit. A **nest-bearing template refuses `count > 1` (409)** before the first mutation: a laser WO's quantity IS the sum of its nests' `planned_runs`. The batch is **all-or-nothing** — the router holds exactly ONE `atomic_transaction` and it wraps the LOOP, never each copy (`atomic_transaction` is not re-entrant), and sequential numbering inside it works only because `_copy_header` flushes before returning (the advisory lock is re-entrant and protects nothing intra-transaction). The response is `WorkOrderTemplateUseResponse`, a strict superset of `WorkOrderDuplicateResponse` by SUBCLASSING (the shared result view dereferences the singular `work_order`): `work_orders[0]` IS `work_order`, plus `created_count`, and both skip lists are the batch's deduped UNION. One `USE_TEMPLATE` audit row per created WO, each carrying `unit_number` + `batch_id`/`batch_size`/`batch_index` (stamped for a single use too — one code path). Editing the source changes what the template produces (intended — which is why every read returns a **live** plan summary, never a stored one), and **a deleted source changes nothing**: the template reads THROUGH the tombstone, the summary is still computed, and `use` still produces a DRAFT (owner decision 2026-08-27, overriding the original refuse-on-deleted design — *"templates need to stay even if there is no work order present for it"*). Only the refusal was dropped, never the signal: `plan.source_work_order_deleted` discloses it on every read, and `plan.available` now means the much narrower "the source ROW could not be resolved at all". **That read-through is safe rather than lucky, and the reason is the one nobody would rediscover**: `work_order_templates.source_work_order_id` is `NOT NULL` with a plain FK and **no `ON DELETE`**, so the referenced row can never physically vanish and *"no work order present"* can only ever mean **soft-deleted** — the plan is always still there to read, which is exactly why a frozen snapshot of it would buy nothing (see the model docstring for why that alternative stays rejected). That FK guarantee used to be an accident; it is now load-bearing, so `DELETE /work-orders/{id}?hard_delete=true` refuses **409** naming the templates saved from the job rather than orphaning one, and soft delete is deliberately unaffected. The half that stays gated is **saving** a template from a deleted work order — still 404 (`resolve_catalogable_work_order`): an already-saved template is a catalog entry, a new one is a fresh selection, which is the invariant-3 line. See `docs/WORK_ORDER_TEMPLATES.md`.
  - **A laser nest's sheet descriptors are canonicalized on write** by `services/laser_nest_text.py` (`normalize_material` / `normalize_thickness` / `normalize_sheet_size`, or `normalize_nest_descriptors` for all three). `LaserNest.material` / `.thickness` / `.sheet_size` carry **no `Part` FK** — sheet recognition on this path is a deliberate heuristic — so the *string* is the only grouping key anything has, and the values come from an LLM extraction that spells one sheet several ways (a 2026-08-06 prod reconciliation split one sheet across two rows on whitespace alone: `144x60` vs `144 x 60`, 25 rows for 19 real specs, every group under-reporting). **Every** seam that writes a nest normalizes — the extraction mapper, the filename-inference fallback, the package build, the manual create, `PATCH /laser-nests/{id}`, and the work-order duplicate copy (canonicalized on the way across rather than copied byte-for-byte — the one field group on that path that is deliberately *not* verbatim, so duplicating a pre-normalization job can't re-inject a legacy spelling). The rule is **normalize spelling, never meaning**: trailing zeros are preserved (`0.250` stays `0.250` — precision on a thickness isn't the normalizer's to rewrite, and the accepted cost is that `0.25`/`0.250` still group apart), units are never inferred, `SS` is never expanded to `304 SS`, and anything unparseable passes through whitespace-collapsed rather than mangled. The transform is idempotent — the seams deliberately overlap. Forward-only; pre-existing rows are untouched.
  - **Reading material ties for display** goes through `services/material_tie_view.py` — the one batched tie + on-hand read shared by the dispatch board and the kiosk queue. Pure read, no write path; keep it that way (a poll is not an actor and records no reason).
  - **Folding two SKUs into one** goes through `services/inventory_combine_service.py` (`build_combine_preview` + `combine_inventory`, behind `POST /inventory/combine/preview` and `POST /inventory/combine`) — a numbering recut can leave two part numbers naming the same physical article, and this moves the stock across without inventing or destroying a unit. It is neither a receive (which mints) nor an issue against a fabricated work order (which destroys and launders the quantity through a production record that never happened): per moved lot line it writes **two linked `ADJUST` rows that sum to exactly zero**, `reference_type='inventory_combine'`, `reference_id` = the `inventory_combines` header (migration `085`). Deliberately **not** a new `TransactionType` member — that means an `ALTER TYPE` on live Postgres plus a value every consumer cannot yet see, for a labelling gain — and deliberately **outside** both `uq_wo_inventory_*` predicates and `work_order_ledger_filter`'s three shapes, so it can never collide with the backflush guards and never appears as work-order material in job costing. Load-bearing beyond that: the **preview writes nothing structurally** (it takes no `AuditService` and no actor id) and is a snapshot, never authorization — the write re-runs every probe under its own row locks; **every refusal is raised before the first mutation**, from one shared probe list so the dialog's words and the write's 409 cannot disagree; **traceability follows the material** onto a newly created target row (lot, serial, cert, heat lot, supplier, PO, dates) while **cost is never reblended** (a new row copies the source's `unit_cost`, an existing one keeps its own); the source part is **never deleted**, only optionally deactivated; and three reservation rules hold — row-level `quantity_allocated`, row-level lot **pins**, and part-level open ties, the last two computed on `eligible_available` rather than `total_on_hand`. Drain and lock order are both ascending stock-row id, and the per-line audit writes are **buffered until after the drain loop** because the audit chain lock is global and taking a row lock behind it deadlocks against a concurrent `/receive`. The paired part-retirement verbs are `POST /parts/{id}/deactivate` / `/activate` — the **only** non-delete writers of `parts.is_active`, which doubles as the soft-delete mask, so don't put `is_active` or `status` on `PartUpdate`. See `docs/API.md` → Inventory → "Combining two SKUs".
  - **Spreadsheet exports go through `services/export_safety.py`** — XLSX via `write_cell` / `append_row` / `harden_workbook` (pins any `str` cell to `data_type="s"` so openpyxl can never emit an `<f>` formula element; non-destructive, values byte-exact, numerics stay numeric); CSV via `sanitize_csv_row` / `sanitize_csv_mapping` (leading `'` on formula-initiating values that aren't plain numbers — lossy on the artifact, **never** on stored data). **Header rows too**: `columns` is a request query param on every `/exports/*` endpoint. Wired into `export_service.py`, `estimate_workbench_export_service.py`, `analytics.py`, `visitor_logs.py`; import *readers* and the static template builder are deliberately untouched. Don't hand-roll a new exporter.
- `models/` — SQLAlchemy 2.0 declarative models (~49). All extend `Base` from `app.db.database`. `work_order_material.py` (`work_order_material_allocations`) is the optional work-order↔material tie the consumption engine reads.
- `schemas/` — Pydantic 2 request/response contracts. Keep API I/O typed through these. **Response schemas inherit `UTCModel`** (`app/schemas/base.py`), not bare `BaseModel`, so `datetime` fields serialize as UTC ISO-8601 with a trailing `Z` (via `core.time_utils.to_utc_iso`); `date`-only fields are unaffected. Hand-built response dicts must run datetimes through `to_utc_iso(...)`. Invariant: **store UTC, serve UTC (`Z`), display Central.**
- `db/mixins.py` — shared model behavior (see invariants below).
- `jobs/` + `worker.py` — ARQ async jobs on Redis (email, MRP runs, long tasks). Enqueue from services; don't block request handlers.
- `core/` — cross-cutting: `config.py` (settings), `security.py` (JWT/bcrypt), `cache.py`, `pagination.py`, `realtime.py`/`websocket.py`, `validation.py` (reusable Pydantic annotated types).
- `mcp/` — the API served to agents as **MCP tools** (`docs/MCP.md`). **The router is the boundary**: a tool call becomes an HTTP request into `app.main:app` (in-process `httpx.ASGITransport`, or HTTPS to `WERCO_ERP_URL` from the stdio bridge) carrying the caller's own access JWT, so `get_current_user` / `get_current_company_id` / `require_role` / `get_audit_service` all run as they would for the SPA — nothing in the package imports a service, builds a user or opens a session, and a 401/403/409 from the route is returned verbatim as an `is_error` result. The catalog is `app.openapi()` at startup (every secured operation outside `catalog.EXCLUDED_TAGS`; route docstrings are now agent-facing tool descriptions), names are derived (`naming.py`: operationId prefix, collisions get `<tag_slug>_` on **every** member, so a generated name can shift when a router adds a twin) and the 13 fixed-name convenience tools in `convenience.py` **shadow** 14 raw routes (`SHADOWED_OPERATIONS`: WO create/duplicate/release/add-operation, both nest-package imports, and the `search` / `work-centers` / `work-orders/{id}` / `shop-floor/dashboard` / `inventory` / `purchase-orders` / `ncr` / `parts` list-reads) so the agent rules have exactly one door: `create_work_order` and `duplicate_work_order` always land DRAFT (the route has no `status` input; the tool strips it and post-checks), `release_work_order` is the only release, `import_laser_nest_package` PUTs the born-RELEASED child back to DRAFT unless `release=true` (a failed demote is a loud `IMPORT SUCCEEDED, BUT…` error) and refuses a target carrying manual nests (`operations[].laser_nest.cnc_file_name` null), and `add_operation` refuses file-path / `.dxf`-style / `Part Detail` names rather than rewriting them. The HTTP door (`http.py`, `mount_mcp` at the bottom of `main.py`, lifespan entered in `lifespan`) is **off by default** (`WERCO_MCP_HTTP_ENABLED`), an exact `Route` at `WERCO_MCP_HTTP_PATH`, stateless (safe behind `WEB_CONCURRENCY=2`), exempt from `MAX_JSON_BODY_BYTES` and the outer rate limit on that path only (bounded by `WERCO_MCP_MAX_UPLOAD_BYTES` instead; the inner route hit is kept). `python -m app.mcp --print-catalog` dumps the tool list (no DB, no token) — run it and quote real names before writing docs or prompts. `tests/test_mcp_smoke.py` is the guard that ships with the package (>600 generated tools, unique wire-valid names, shadow set disjoint, collisions prefixed, door exempt from the outer limit); the per-tag coverage guard — every `catalog_tags(app.openapi())` tag outside `EXCLUDED_TAGS` has ≥1 tool — is the CI trip-wire for "a new router shipped and MCP is blind", and `EXCLUDED_TAGS` is the honest exclusion set it must use.

API style: REST, JSON, OpenAPI at `/docs`. JWT auth — 15-min access token, 7-day refresh, and a 7-day `SESSION_ABSOLUTE_TIMEOUT_HOURS` window that despite its name is an **idle** window, not a hard ceiling: `POST /auth/refresh` re-mints through `create_refresh_token`, which recomputes the `absolute_timeout` claim from now, so every refresh restarts it. Password policy is length + blocklist (12 chars, no common substring) with **no** character-class rules — NIST SP 800-63B 5.1.1.2; see `validate_password_strength`.

## Frontend architecture

React 19 SPA under `frontend/src/`:

- `pages/` — route-level screens (~59). `components/` — reusable UI grouped by domain.
- `services/` — Axios API client with **ETag-based conditional caching and a refresh-token interceptor**. Route API calls through this client, not raw axios.
- `context/` — React Context for cross-cutting state: auth, active-company switching, keyboard shortcuts, tours. No Redux; server data is fetched per-page and cached at the client.
- Forms: React Hook Form + Zod (`validation/`). State that should survive reload (pagination, filters) goes in URL params. Shared create/edit forms wrap each control in the `<FormField>` primitive (`components/ui/FormField.tsx`, barrel-exported) rather than a bare `<label>` + input — its render-prop hands the control the `id`/`aria-describedby`/`aria-invalid`/`aria-required` wiring so the label is programmatically associated and errors are announced, and it renders the required-marker and error chrome consistently (works for native inputs and `<SelectField>`). A single-select over a list too long to scan (hundreds of stock parts) uses the shared `<ComboBox>` (`components/ui/ComboBox.tsx`, barrel-exported) instead of a native `<select>` — type-ahead over label + hint, ARIA 1.2 combobox wiring, and a listbox **portaled to `document.body` at `z-[70]`**, one layer above `<Modal>`'s `z-[60]`, because the first caller sits in a table inside `overflow-auto` where an in-flow listbox is clipped. Two things about it are load-bearing rather than stylistic: it is hand-rolled rather than Headless UI's `Combobox` (whose v2 `anchor` positioning runs on floating-ui and needs a `ResizeObserver` polyfill `setupTests.ts` doesn't carry, so every suite rendering one would need a global polyfill to mount a UI control), and **Escape is intercepted by a capture-phase `window` listener**, not a React `onKeyDown` — `<Modal>` closes on a bubble-phase `window` keydown and both portal to `document.body`, so a React `stopPropagation()` does not sit between them; measured, one Escape closed the popup *and* the enclosing wizard, discarding every row the planner had corrected. `components/laser/SheetPartPicker.tsx` is the reference wrapper (a default filter with a "show all" escape hatch, on-hand hints, and the current selection always pinned into the list so a filter can never blank a pre-filled value). Unsaved-edit protection comes from the `useUnsavedChanges(isDirty)` hook (`hooks/useUnsavedChanges.ts`): a `beforeunload` guard for refresh/tab-close plus a `confirmDiscard()` gate to call from Cancel/Close handlers (in-app SPA route-change blocking is *not* available — the app mounts the component `<BrowserRouter>`, so react-router's `useBlocker` has no data-router context to hook into). Customers/Users/Materials/PartsNew/PartEdit/WorkOrderNew/BOM were the original reference adopters; the guard is now standard on create/edit forms (incl. the long Purchasing/Receiving/Quality/CustomerComplaints/Calibration modal forms and the ProcessSheets editors) — new forms should wire it too.
- Styling: Tailwind CSS 4 + DaisyUI, with the Werco brand palette (werco-navy `#1B4D9C`, accent red `#C8352B`, steel grays) and an "instrument-panel" aesthetic — sharp corners, hairline borders, minimal shadows. Match it. Panel surfaces use the canonical `bg-fd-panel` token (don't hard-code the panel hex). The `fd-*` Foundry tokens resolve CSS variables (`--fd-*` in `index.css`), not baked hex, so a scope class can re-theme a subtree — the kiosk surfaces put `.fd-scope-kiosk` on their roots for the darker kiosk palette; everywhere else the `:root` values keep every `fd-*` utility rendering exactly as before (opacity modifiers like `bg-fd-red/10` still work — Tailwind v4 emits `color-mix()`).
- Modals/dialogs: build with the shared `<Modal>` primitive (`components/ui/Modal.tsx`), not hand-rolled `fixed inset-0` overlays — it portals to `document.body` at `z-[60]` (clearing the fixed `z-50` sidebar) and normalizes the instrument-panel panel chrome, backdrop/Escape close, modal stacking, and focus management (focus-into-panel on open, Tab/Shift+Tab focus trap with wrap, focus-restore on close — topmost-only in a nested stack). A few non-dialog overlays (mobile sidebar backdrop, Tour spotlight, GlobalSearch's Headless UI palette, CopilotPanel side panel, LoadingOverlay) are intentionally not Modals. Two shared dialog primitives build on it, both barrel-exported: `<ConfirmDialog>` (`components/ui/ConfirmDialog.tsx`) for confirm/cancel decisions, and `<InputDialog>` (`components/ui/InputDialog.tsx`) for single-field text capture (blocker notes, saved-filter names) — FormField-labeled, Enter submits, and the value reaches `onSubmit` trimmed and never empty. Both take a `pending` prop for server-gated actions (per the non-optimistic convention below): while in flight the confirm/submit button shows the LoadingButton spinner + double-click guard, Cancel is disabled, and backdrop/Escape dismissal is refused — pass `pending`, not a `confirmLabel` ternary. Closing is the caller's job (via `open`), so a refused submit can keep the dialog up and close only on success. Native `prompt()` is gone from the app — reach for InputDialog, don't reintroduce it. Native `confirm()` is likewise gone from application code, with exactly one deliberate survivor: `useUnsavedChanges`'s `confirmDiscard()` (`hooks/useUnsavedChanges.ts`) stays `window.confirm` because callers wire it as a synchronous boolean gate in Cancel/Close handlers (`if (confirmDiscard()) close();`) — everywhere else reach for `<ConfirmDialog>`, don't reintroduce it.
- Async-state feedback is standardized — don't hand-roll it. User feedback (success/error notices) goes through `useToast()` (`components/ui/Toast.tsx`), never `alert()`. It carries a fourth variant beside success/error/info: **`warning`** — for an action that SUCCEEDED but did not do everything asked (a partial result the user has to act on). `success` would hide the shortfall and `error` would claim a failure that did not happen, sending someone looking for a record that exists. It renders amber and, like `error`, uses `role="alert"` so it interrupts the screen reader. First caller: a duplicated work order that could not carry a material tie across. A failed data load renders the shared `<ErrorState>` (`components/ui/ErrorState.tsx`) with a Retry button that re-runs the fetch, not a blank section. A "no rows" placeholder renders the shared `<EmptyState>` (`components/ui/EmptyState.tsx`). All three are exported from the `components/ui` barrel. **Server error `detail` is safe to display directly:** the Axios interceptor (`services/api.ts` → `normalizeAxiosErrorDetail` in `utils/apiError.ts`) collapses FastAPI 422 `detail` arrays to a joined string before any `.catch` sees them (structured 409 objects / plain strings pass through), and `App.tsx` wraps everything — outside every provider, incl. `ToastProvider` — in a global `<ErrorBoundary>`. Don't render a raw `detail` from a bare-`axios`/`fetch` call (run it through `toDisplayString()`), and don't mount providers outside the global boundary. See docs/DEVELOPMENT.md → Frontend API error handling.
- Perceived-performance hooks (`hooks/`): `useOptimisticMutation` generalizes the optimistic-update + rollback pattern (apply the UI change synchronously before awaiting the server; on failure roll back and surface the server's verbatim `detail` as an error toast — never a success toast for a failed call); `useDebouncedValue(value, delayMs)` debounces list-search inputs so the filter/query doesn't fire on every keystroke (the standard list-search pattern — ~14 list-page adopters; don't hand-roll a `setTimeout` debounce); `useScrollRestoration` does manual window-scroll save/restore per route, wired **once** in `Layout.tsx` (the app mounts a plain `<BrowserRouter>`, so react-router's data-router `<ScrollRestoration>` isn't available — same constraint that rules out `useBlocker`). **Convention (compliance-relevant): optimistic UI is only for rarely-rejected actions** (ActionInbox accept/dismiss/snooze, WorkOrders delete, notification/egress toggles). Server-GATED actions whose whole point is that the server may refuse — WO release-readiness, shop-floor sequence/predecessor gating — must stay **non-optimistic** (keep a loading state, reflect only what the server returns) so the UI never shows a state the server would refuse.
- Standard action buttons use the shared `<Button>` primitive (`components/ui/Button.tsx`, barrel-exported) — a `variant` (`primary`/`secondary`/`danger`/`ghost`) + `size` (`sm`/`md`) typed wrapper over the instrument-panel `.btn-*` classes, not raw `<button className="btn-primary ...">`. For an async action that needs an in-flight spinner / double-click guard, reach for `<LoadingButton>` instead (same `variant`/`size` vocabulary).
- Status badges color through the central `utils/statusColors.ts` source of truth — the single canonical status→variant map (5 semantic variants: green/blue/amber/red/slate). Render via `<StatusBadge>` (which now defaults to this map) rather than per-page status-color maps, so a given status looks identical everywhere (e.g. `in_progress` is canonically blue). A `colorMap` override stays available for genuinely page-specific labels.

Sort/paginate/group are pure (never mutate the `data` prop). Pass `serverPagination` (page/pageSize/hasNext/onPageChange) for offset-paged endpoints where the full set isn't client-side; otherwise pass `pageSize` for client paging. WorkOrders/Inventory/Purchasing (client sort+paginate+CSV), AuditLog and Inventory's Stock Movements tab (server pagination), and WorkCenters (grouped-by-type) are the reference usages.

## Compliance-critical invariants

These are the rules that keep tenant data safe and the quality system trustworthy. Treat violations as bugs.

**None of these are CMMC artifacts, and descoping CMMC relaxes nothing in this list.** Invariants 1–4 are multi-tenant data security and correctness — they would hold for any SaaS, and two of them exist because of real incidents (the 2026-07-07 Supabase exposure, the lost-update bugs behind PR #141). Invariants 5–6 serve the AS9100D/ISO 9001 quality system, which remains in scope. The genuinely CMMC-specific machinery is elsewhere and is tracked in the frozen `docs/CMMC_LEVEL_2_COMPLIANCE.md`.

1. **Tenant isolation.** Most domain tables carry `company_id` via `TenantMixin` (`app/db/mixins.py`), `nullable=False`. Every query against tenant data MUST be scoped to the active company — use `tenant_query()` / `tenant_filter()` from `app.db.tenant_filter` and derive the company from `get_current_company_id`. A query that returns another tenant's rows is a security defect.

2. **Audit logging.** State changes (create/update/delete/status-change) must be recorded through `AuditService` (`services/audit_service.py`) via its `log_create` / `log_update` / `log_delete` / `log_status_change` helpers — obtained from the `get_audit_service` dependency. Never write to the `audit_log` table directly or backfill rows out of band — that rule is unconditional. Its tamper-evidence has **two independent layers**: (a) the DB-level `008`/`060` triggers that refuse `UPDATE`/`DELETE` — always on, no setting affects them; (b) the SHA-256 hash chain (`sequence_number`, `previous_hash`, `integrity_hash`), which is on by default but **runtime-pausable** via `AUDIT_HASH_CHAIN_ENABLED` (default `True` = today's exact behavior). Paused, rows are still written with identical content, but allocation moves to a lock-free Postgres sequence, `previous_hash` is `NULL`, and `integrity_hash` is the `LEGACY_CHAIN_PAUSED` placeholder every verifier consumer already skips; gaps inside that window are normal (`IntegrityReport.legacy_sequence_gaps`), not tampering. **Pausing is not fully reversible** — paused rows can never be made verifiable retroactively and gap-based deletion detection is permanently gone across the window. Don't describe the chain as unconditional; see `docs/AUDIT_LOG_RETENTION_RUNBOOK.md` → Pausing the hash chain.

3. **Soft delete, not hard delete.** Models using `SoftDeleteMixin` are deleted via `.soft_delete(user_id)` (sets `is_deleted` / `deleted_at` / `deleted_by`). Queries must filter `is_deleted == False`. Don't issue physical `DELETE` on these. As of migration `071`, `Vendor` / `PurchaseOrder` / `POReceipt` / `NonConformanceReport` are soft-deletable too (vendor/PO delete+restore, NCR void+restore, receipt void — each guarded, requiring a reason where destructive, and audited). Reversing a *posted* effect (a receipt correction/void that unwinds inventory) never mutates the historical ledger row: it appends a **signed compensating transaction** (`InventoryTransaction` `ADJUST`) — the "compensating-transaction + required-reason + audit" reconciliation pattern shared with inventory adjust. These delete/correct/void controls are server-GATED (the server may refuse — e.g. an inspected receipt, a still-blocking NCR, a PO with received material), so per the optimistic-UI convention above they stay **non-optimistic**. **`tenant_query()` / `tenant_filter()` scope `company_id` and nothing else — neither filters `is_deleted`**, and an `is_active`-style flag that a delete happens to clear on the way out is a *mask*, not a filter. Every read of a soft-deletable model needs its own `is_deleted == False`: that is the trap behind the 2026-08-16 `Vendor` sweep, where most vendor query sites carried no tombstone filter and six of the ones that looked safe were masked only because `delete_vendor` also sets `is_active=false` — a mask a single blind-`setattr` `PUT` could clear on all six at once. For a by-id resolve, build a `_live_<thing>_or_404` helper (`purchasing.py` carries `_live_po_or_404` and `_live_vendor_or_404`) rather than sprinkling the filter, and name the deliberate non-users in its docstring — the exceptions are real: **delete** must see the tombstone to refuse a double delete, **restore** to undo one, a **duplicate probe** must keep matching deleted rows wherever the unique constraint has no partial predicate (a deleted vendor still owns its code), and a **historical record** — a PO's vendor, a lot's supplier — must keep naming who it named. That last exception is about *records vs. selection*, not reads vs. writes: some **writes** are records too, and stay open to a removed vendor on purpose (a supplier cert or MTR arriving after the relationship ends, a closing scorecard or the supplier audit that documents *why* the supplier was removed — AS9100D 8.4 expects those, and gating them makes the record of the removal the one record nobody can file). What gets gated is *selection and permission*: raising a live PO, binding a dock-scan routing rule, entering or re-approving a supplier on the ASL — and on a blind-`setattr` update verb the gate must be repeated, since those resolve by their own id and never re-read the vendor. So the rule is per-site: filter, or carry a comment saying why not. **And a restore returns the RECORD, not the permission.** Where a delete also clears an approval-ish flag, the restore must put back the value that flag had *before* the delete rather than hard-coding the permissive one — `restore_vendor` sets `is_active = COALESCE(is_active_before_delete, False)` (migration `082`) so a supplier the shop deliberately switched off cannot be re-approved as a side effect of somebody undoing a delete; AS9100D 8.4 treats the approved-supplier list as controlled, and the same logic guards any `is_approved`/`is_active`-shaped flag. Remember the prior value in a nullable sidecar column written by the delete and **cleared** by the restore, and keep it out of the request schemas so no `PUT` can pre-seed what the restore will read back. **An unrecoverable prior value resolves to the RESTRICTIVE setting, not to the old permissive default** — NULL means the row was deleted before the sidecar existed, so the flag is genuinely unknowable, and by owner decision (2026-08-16) a vendor in that state restores **inactive**, deliberately breaking the pre-`082` unconditional re-activate rather than preserving it. The asymmetry is the argument: restoring too restrictively costs one explicit audited re-activation and is visible immediately, while restoring too permissively is indistinguishable from a legitimate approval and so is never detected. **That argument only holds if the re-activation is actually performable from the UI, so shipping the restrictive restore obliges you to ship the screen that undoes it** — a restored-inactive vendor is invisible on every default list (`GET /purchasing/vendors` is `active_only`, global search filters `is_active`, the PO picker takes approved-and-active only), which is why Purchasing → Vendors carries a three-way **Active / Inactive / Deleted** switch and not the two-way one the Orders tab has; the Inactive view's Edit button is the audited `PUT` that reactivates. Pair it with a pre-click disclosure too: the deleted view ships `is_active_before_delete` so the archive's "Restores As" column can say which rows come back switched off *before* the operator clicks, rather than only a toast afterwards. Forward-only, never backfilled, and never tightened to NOT NULL, since NULL is what encodes "deleted before the column existed". The tempting shortcut — stop writing the mask on delete so the restore has nothing to put back — is a **security regression**, for the reason the paragraph above gives: the mask is a deliberate second layer, and dropping it silently changes what "deleted" means to every query added later.

4. **Optimistic locking.** Models with `OptimisticLockMixin` carry a `version` column — respect it on concurrent updates rather than blind overwrites. On the contended write paths the lock is SQLAlchemy-enforced: `WorkOrder`, `WorkOrderOperation`, and `TimeEntry` map `version_id_col` directly (deliberately not via the mixin — see its docstring in `app/db/mixins.py`), so a concurrent stale write raises `StaleDataError`, translated to HTTP 409 by endpoint-local handlers plus an app-wide handler in `app/main.py`.

5. **Traceability & revisions.** Parts/BOM carry revision control and critical-characteristic flags; lot/serial traceability is a product requirement. Preserve historical records — prefer new revisions over mutating shipped data.

6. **Material consumption.** Material is optionally tied to a work order (or one of its operations) by a `work_order_material_allocations` row; consumption depletes stock as work completes, via `services/material_consumption_service.py` wired into **two** seams — `apply_operation_completion_inventory_effects` (operation completion, one operation's ties) and `apply_completion_inventory_effects` (work-order completion, the whole-WO self-heal). Add completion side-effects to those seams, never at their call sites. Four rules: (a) it is **sum-delta / reconcile-to-target** — `target = qty_per_run × (op complete + scrapped)`, post the positive delta only — so replays and reconcile-on-read converge without a new unique index. **Timing: stock leaves when an OPERATION completes** — `apply_operation_completion_inventory_effects` runs right after `finalize_operation_completion` on all four operation-completion handlers and consumes **that one operation's** ties, so a laser WO deducts nest 1's sheets when nest 1 closes. Work-order completion still runs the whole-WO reconcile, but as the **self-heal**, not the moment stock moves. It is deliberately **not per-run**: an operation that is still `IN_PROGRESS` is still reducible, and consumption never auto-reverses, so consuming against one could strand material nothing can give back — scope stays one *completed* (hence reduce-immune) operation; (b) it **never auto-reverses** — a negative delta is a no-op, and un-consuming is an explicit, reasoned, audited compensating transaction (the receiving-correction pattern), never automatic, because this path also runs from a GET where there is no actor intent and no reason; (c) consumption rows post one of **two** reference shapes, both deliberately **outside** the `uq_wo_inventory_receipt`/`uq_wo_inventory_issue` partial predicates: operation-scoped ties post `reference_type='work_order_operation'` (`reference_id` = the operation) so they can never collide with the backflush idempotency guards, and the reconciled component leg — BOM/routing demand *and* work-order-scoped ties — posts `reference_type='work_order_backflush'` (`reference_id` = the work order) because reconcile-to-target needs N rows per (WO, part) plus a later top-up row, which those one-row indexes cannot express. Both also carry `inventory_transactions.allocation_id` when a tie drove them (a BOM-driven row has it NULL — that is how the two nets stay disjoint). Counting the legacy/FG `reference_type='work_order'` shape, that is **three** reference types, and anything reading work-order material must read **all three** — go through `work_order_ledger_filter` in `app/db/ledger_filter.py` rather than re-declaring the predicate (`traceability.py`, job costing, analytics and `GET /inventory/transactions?work_order_id=` all do); `_component_already_issued` stays keyed on `'work_order'` alone, on purpose, as the permanent fence over pre-PR-4.4 rows; (d) an **untied work order must stay byte-identical** to its pre-feature behavior — no ledger row, no audit row, no event. Allocation rows are never physically deleted (`status` is the tombstone, not `SoftDeleteMixin`), and `qty_consumed` is a cache — the ledger is authoritative. The **BOM/routing half** of the reconciled leg is additionally opt-in per part: `Part.backflush_components` (default off) is settable **only** on `PUT /parts/{id}` / `PUT /materials/{id}` — one shared gate, `parts.assert_backflush_change_allowed`, imported into both because they write the same `parts` rows — which refuses **409** on any blocking readiness diagnostic and runs *before the first `setattr`* so a refusal leaves the row untouched. Its two read companions, `GET /parts/{id}/backflush-readiness` and `GET /work-orders/{id}/backflush-preview`, are **pure reads that write nothing** — no ledger row, no audit row (in particular no `BACKFLUSH_DOUBLE_ISSUE_BLOCKED`), no event; that is structural (the resolution layer takes no `AuditService`), and keeping it structural is the rule, not a convention.

## Migrations — handle with care

There are 37+ Alembic versions over live, multi-tenant data. When adding a migration:
- Make it **idempotent and reversible** (provide a real `downgrade`). The most recent commit history shows migrations being hardened for idempotency — follow that precedent.
- Never edit a migration that has already been applied; add a new one.
- New tenant-scoped tables need a non-null `company_id` + index (the `TenantMixin` shape). And **every** new table needs `ENABLE ROW LEVEL SECURITY` in its migration (Postgres-only, like `059`) — the prod Supabase posture is deny-by-default RLS with zero policies (app-layer tenancy stays the enforcement; the Security Advisor lints RLS state, so an RLS-less table re-flags the `rls_disabled_in_public` ERROR). See `docs/SUPABASE_SECURITY.md`.
- Autogenerate is a starting point — review the diff; SQLAlchemy doesn't always detect enum/constraint changes.
- Autogenerate only sees tables registered on `Base.metadata` — every model module must be imported in `app/models/__init__.py` (`alembic/env.py` does `from app.models import *`). Adding a model file without wiring it in there makes autogenerate miss it or crash with `NoReferencedTableError`.
- **Bootstrap is not `alembic upgrade head`.** On an empty Postgres the schema is created by `Base.metadata.create_all()` on first boot (not by an initial migration; `001` only adds indexes), so the path is `create_all` → `alembic stamp <baseline>` → incremental `upgrade`. A bare `upgrade head` on an empty DB fails (`002` does `ALTER TYPE workcentertype`). Never stamp past DDL `create_all` can't reproduce — and that means anything not mirrored in the models, not just raw SQL: prod lost the `008` audit triggers this way (2026-07-07), ~42 read-path indexes declared only in migrations `001`/`003`/`020`/`026`/`027` the same way (found 2026-07-31; restored **and mirrored into the owning models' `__table_args__`** by `079`), and — same audit, against `pg_constraint` — `003`'s 22 named lineage FKs and its `chk_*` value-range CHECKs (restored and mirrored by `080`). Stamp at `058` so `059`/`060` run, and mirror any migration-only index/constraint in its model in the same PR (the `042`/`078`/`079`/`080` lock-step convention). **Four of `003`'s constraints are deliberately NOT restored** — `chk_inventory_items_quantity_non_negative` (invariant 6's shortage posture lets a short completion drive a lot negative), `chk_po_receipts_quantity_received_positive` (receipt void writes 0), `chk_bom_items_quantity_positive` (a non-positive BOM line is a representable state the backflush diagnostics exist to surface), and `chk_work_centers_efficiency_range` (targets a column that never existed). Don't "complete the set"; a guard test in `tests/test_migration_080_restore_stamped_over_constraints.py` refuses it. See `docs/DEVELOPMENT.md` → Database Migrations for the full remaining stamped-over hazard list.

## Conventions worth matching

- Backend line length is 120 (flake8/black configured to it). Status/priority/role values are `str`-backed `enum.Enum` classes co-located with their model.
- Keep routers thin and push logic into `services/`; keep query scoping in `db/tenant_filter` helpers.
- `operation_number` (`WorkOrderOperation` / `RoutingOperation`, `String(20)`) is an **identifier, not a display label** — store the bare sequence (`"10"`), never `Op 10`. Minting the label into the column is what made the kiosk read "Op Op 10": every render site prefixes it again. The `Op ` prefix belongs to render time, via `frontend/src/utils/operationLabel.ts` — `formatOperationLabel` for a free-standing value, `operationNumberText` under a column header that already says "Op" (the second is implemented by peeling the first, so the two cannot drift). It is user-editable free text and **forward-only, never backfilled**: legacy `Op 10` rows persist by design, because an `UPDATE` would mutate released quality plans with no `AuditService` row (invariant 2) and could not tell a minted value from an office-typed `OP-10A` a customer's numbering requires. Convergence happens at the display layer instead. Only two consumers parse it, both by extracting digits (SPC critical-dims matching; `_normalized_operation_number` behind the completion-evidence reconcile key) — don't add a third that slices, sorts or compares. `POST /routing/{id}/operations/reorder` is the one path that rewrites the column, draft routings only. See `docs/DEVELOPMENT.md` → Operation numbers.
- Frontend: typed API responses, forms via RHF+Zod, brand palette + instrument-panel styling. Datetimes arrive over the wire as UTC `Z`; render **all** timestamps in shop-local Central time (America/Chicago) via `utils/centralTime.ts` (`formatCentralDateTime` / `formatCentralDate` / `formatCentralTime`; `toDate` to parse — it treats zone-less strings as UTC; `getCentralTodayISODate` / `getCentralDateStamp` for date-only form defaults). Never `new Date(x).toLocaleString()` for display — it renders in the viewer's timezone and mis-parses no-`Z` strings.
- Accessibility: the jsx-a11y debt is **burned down and fully enforced** (all three families flipped `off`→`error`). Keep it green: icon-only buttons need an `aria-label` (reuse any `title`); form fields get a real associated `<label>` via the shared **FormField** primitive (or `htmlFor`+`id` for inline/filter controls); clickable non-interactive elements must be a native `<button>` or carry a literal interactive `role` + `tabIndex` + `onKeyDown` (and `e.target===e.currentTarget` guard when they wrap focusable children). `control-has-associated-label` runs with the plugin's recommended options (it ignores `input`/`textarea`/`tr`, so don't add redundant labels there). Don't suppress per-line. The Getting-Started tour **auto-starts once per user on first login** (per-user localStorage flag; skip/dismiss is respected and does not re-trigger) — see `src/data/tours.ts` (`shouldAutoStartGettingStarted`) wired in `Layout.tsx`.
